# 02｜技术架构与包设计

## 1. 分层

```text
业务应用（React / Vue / Next.js / Nuxt）
           ↓ 仅安装自己的框架包
ui-react                         ui-vue
hooks + React DOM                composables + Vue SFC
           ↘                  ↙
       internal-core / internal-dom（私有源码，构建内联）
        状态、集合、校验 / 定位、焦点、滚动锁
                       ↓
              ui-theme → ui-tokens
     框架无关 CSS、主题预设    token 数据及基础变量
```

React 与 Vue 的组件行为、状态枚举、部位名和语义 token 一致；框架惯用 API 不必字面一致。不要用正则把 React 转 Vue，不使用一个框架包依赖另一个框架包。

## 2. 包职责与依赖

| 包目录 | npm 名称 | 是否公开 | 内容 | 运行时边界 |
|---|---|---|---|---|
| tokens | `@your-scope/ui-tokens` | 是 | 原始/语义 token、schema、生成 CSS/JSON/TS | 不依赖框架或 DOM |
| theme | `@your-scope/ui-theme` | 是 | 主题工具、预设、基础结构 CSS、各组件外观 CSS | 依赖 tokens，不访问 DOM |
| react | `@your-scope/ui-react` | 是 | React 组件、hooks、类型、样式别名 | peer React/react-dom，依赖 theme |
| vue | `@your-scope/ui-vue` | 是 | Vue 组件、composables、类型、样式别名 | peer Vue，依赖 theme |
| internal-core | 私有 | 否 | 集合、受控状态判定、纯状态转换、日期工具 | 构建内联，禁止外部深层导入 |
| internal-dom | 私有 | 否 | effect 时调用的 DOM 工具与定位适配 | 构建内联，不在顶层操作 DOM |
| test-utils / build-config | 私有 | 否 | 跨框架用例、构建脚本 | 仅 devDependencies |

UI 包源码使用 `workspace:*` 依赖 theme；theme 使用 `workspace:*` 依赖 tokens。打包时必须转为有效 semver。私有包不能作为未发布依赖残留在 tarball 的 package.json 中；清理必须由脚本完成并有断言，不能让使用者手动修包。

## 3. 复用方式

共享能稳定表达的纯逻辑，例如选项归一化、状态转换、分页计算、树节点索引与 token 解析。React effect/ref/event 与 Vue watch/ref/emit 分别实现。焦点、弹层层级和滚动锁可共享 DOM 服务，但实例生命周期由适配层控制。

本项目先用小型 TypeScript 状态模块，不强制引入大型状态机运行时。状态复杂度出现明确重复后，使用 ADR 决定是否引入依赖。不要把普通按钮做成通用状态机解释器。

浮层定位优先评估 `@floating-ui/dom`，它只解决定位，不能替代焦点、键盘与可访问性设计。[官方说明](https://floating-ui.com/docs/getting-started)

## 4. 样式关系

两框架使用相同 `data-dui`、`data-part` 和状态属性，消费同一份 CSS。CSS 不依赖 Vue scoped hash，也不依赖 React 生成 class。部位可以有不同内部 DOM，但公开的命名部位与效果契约要一致。

只导入 React 包不得引入 Vue；只导入 Button 不得引入 Table、日期逻辑、上传管理或全量图标。公共入口保持静态 named exports，无默认的全局安装副作用。

## 5. 不采用的方案

| 方案 | 本期不采用的原因 | 何时重新考虑 |
|---|---|---|
| React 套 Vue / Vue 套 React | 双运行时、生命周期与事件边界复杂 | 迁移遗留业务而非基础库 |
| Web Components 统一渲染 | 不作为双框架体验和表单/SSR 的默认折中 | 需要框架无关分发时另立包 |
| 两套现成 UI 库重皮肤 | API、DOM、版本和行为难长期统一 | 用户明确接受依赖与差异时 |
| 完全从零实现所有底层 | 焦点和定位成本高，风险难控 | 小型纯逻辑合理自建 |
| 首期拆 72 个 npm 包 | 版本管理、依赖和发布复杂 | 数据证明单组件包更有价值 |

这些是项目设计选择，不是对所有项目的通用结论。
