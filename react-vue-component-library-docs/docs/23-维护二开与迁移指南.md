# 23｜维护、二次开发与迁移

## 1. 推荐扩展顺序

先 tokens → 部位样式 → slots → 业务包装 → 必要时 fork。业务特有 props 放 AppButton/AppTable 等业务封装，不直接污染通用库。避免每次需求都改 node_modules；小修复可临时 patch 并追踪上游，但不作为长期维护架构。

## 2. 新组件流程

复制组件规格模板，确定应用场景、非目标、API、状态、行为和可访问性；确认是否可组合现有组件；确定优先级与公开级别；实现共享逻辑与双框架；补 CSS/token/导出/文档/测试；做包体审查；有证据后加入组件索引。

不要只复制 Button 文件改名。每个复杂控件先写数据/状态模型，再决定 DOM。依赖没有完成时明确 blocked，不能偷偷引入未审查整套 UI 库救场。

## 3. 主题兼容

token 删除、类型变化、含义改变属于公共变更；先提供旧键映射和开发告警，再在 major 清理。保留主题 schemaVersion；导入旧主题时执行纯数据迁移，并输出变更和不兼容项。

不要默默忽略旧主题所有未知键，让页面退回默认色。迁移脚本提供 dry-run、备份建议与清晰 diff，不覆盖用户文件而无确认。

## 4. 框架升级

先增加新版本 CI 试验矩阵，再修复类型/运行时问题，然后扩大 peer 区间；停止支持旧版本需更新 peer、说明原因、给迁移版本与 semver 处理。React 与 React DOM 必须成对验证；Vue 与相关编译工具链版本协调。

## 5. Fork 规范

使用新的 npm scope，保留原许可署名，更新 repository/bugs/品牌，记录上游 commit；单独维护业务补丁和上游同步分支。不要继续使用原始 scope 造成误认。供应链和安全更新需要持续跟进。

## 6. 支持与问题模板

要求复现最小项目、包版本、框架版本、浏览器/OS、安装工具、导入方式、主题设置、预期/实际、控制台和录屏。敏感数据先脱敏。问题按安装/类型/行为/样式/移动/SSR/无障碍/性能分类。

维护节奏按实际资源确定；不承诺尚无团队保障的 SLA。每个稳定分支明确支持范围和安全处理联系人。
